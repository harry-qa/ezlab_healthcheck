# Playwright 기반 이지랩(ezLab) 서비스 헬스 체크 자동화

[이지랩(ezLab)](https://ezlab.im) 서비스의 배포 후 안정성을 30분 주기로 검증하는 자동화 도구입니다.

## 1. 개요

이지랩 전체 서비스(이지캡처, 이지집, 이지파인더, 이지메모, 이지캠, 이지리더)를 대상으로 서버 생존, API 응답, UI 링크 연결, 다운로드 페이지·파일, 콘텐츠 무결성, 이미지 로딩, 로그인 폼, SSL 인증서 만료를 다국어(ko/en/jp/tw) 환경에서 통합 점검합니다. 수동 점검을 대체해 QA 공수를 절감하고 배포 품질을 확보하는 것이 목적입니다.

## 2. 점검 항목 (9단계)

| STEP | 점검 내용 |
|---|---|
| **1** · 다국어 서버 생존 | `ezlab.im/ko`, `/en`, `/jp`, `/tw` 메인 페이지 HTTP 상태 확인 (워밍업 1회 + 본측정 3회) |
| **2** · API 자동 수집·검증 | 페이지 탐색 중 네트워크 인터셉트(XHR/Fetch)로 내부 API를 자동 수집하고 4xx/5xx 검증 |
| **3** · UI 링크 전수조사 | 내부 링크를 depth 2까지 재귀 탐색. 탭 버튼 전환 페이지도 감지, 다운로드 파일·`mailto:` 는 제외 |
| **4** · 다운로드 페이지 | 서비스 도구 페이지(`/ko/tool/*`) 응답 상태와 다운로드 버튼 존재 확인 |
| **4-1** · 설치 파일 URL | `/api/tools/info` 에서 수집한 실제 설치 파일 URL을 HEAD로 확인, HEAD 차단 CDN만 Range GET으로 재확인 |
| **5** · 언어별 메인 페이지 | 핵심 키워드 존재로 콘텐츠 누락 감지 + 이미지 수집을 한 번의 방문에서 동시 수행 |
| **6** · 깨진 이미지 | OG/Twitter 메타 · 브라우저 실제 요청 · DOM `<img src>` 3계층 판정 |
| **7** · 로그인 폼 렌더링 | 로그인 페이지의 소셜/이메일 버튼 렌더 확인 (ko: 카카오·네이버·구글·이메일 / 그 외: 구글·이메일) |
| **8** · 이지다운 정보 페이지 | 별도 도메인 `ezdown.kr` 의 타이틀·본문·후기·FAQ 렌더 검증 |
| **9** · SSL 인증서 만료 | `ezlab.im` / `ezdown.kr` 인증서 만료일을 TLS 핸드셰이크로 직접 확인 |

주요 판정 기준:

- **STEP 3** — 응답 3초 초과는 SLOW. 점검 페이지 신호("점검중", "서비스 준비중")는 내부 링크의 실제 마크업에서만 검사합니다(번들 문구·외부 링크 오탐 방지).
- **STEP 4-1** — 다운로드가 JS 기반이라 페이지 `a[href*=".exe"]` 로는 URL이 잡히지 않습니다. Range 재확인은 스트리밍 요청으로 보내 206이 아니면 즉시 연결을 끊고, 206이어도 `Content-Range` 형식과 수신 바이트가 정확히 1인지까지 확인합니다. 파일 URL을 한 건도 수집하지 못하면 WARN(커버리지 0을 조용히 통과시키지 않음), 응답 이상은 FAIL입니다.
- **STEP 5** — SPA 하이드레이션 지연 오탐을 막기 위해 재시도 진입 + 본문 렌더 대기 후 판정합니다.
- **STEP 6** — 네트워크 4xx·5xx는 즉시 실패, 200만 관측된 자산은 캐시 히트일 수 있어 요청 URL당 1회 능동 검증(상태 + `Content-Type: image/*` + 본문 크기 > 0)합니다. 304는 정상, 제3자 도메인은 점수에서 제외합니다. 집계는 원본 자산 URL, 판정은 실제 요청 URL 기준입니다(Next 이미지 프록시는 폭마다 URL이 달라 특정 폭만 실패할 수 있음). 관측 구간은 `domcontentloaded`(15초) → `load` 최대 3초 → 안정화 1초로 고정하며 `networkidle` 은 쓰지 않습니다.
- **STEP 7** — 로그인 "입구"의 렌더링만 봅니다. 버튼 클릭 이후 실제 OAuth 성공 여부는 검증 범위 밖입니다. 버튼 누락은 WARN, 페이지 진입 실패는 FAIL.
- **STEP 9** — 만료 D-14 이하 WARN, D-7 이하 또는 만료됨 FAIL(자동갱신 실패 신호로 보고 Slack·이슈 알림).

## 3. 주요 특징

- **다국어 통합 점검**: 한국어·영어·일본어·중국어(번체) 4개 언어를 단일 테스트에서 순회
- **하이브리드 검증**: 서버 응답 + API 인터셉트 + UI 링크 크롤링 + 콘텐츠 검증 + 이미지/로그인 점검을 한 번에 수행
- **WAF 회피**: 일반 브라우저와 동일한 `User-Agent` + 랜덤 딜레이(300~800ms). 딜레이는 링크 검증 요청에만 적용됩니다
- **통합 HTTP 판정**: 공개 경로는 2xx·3xx만 정상. 400·405·408·429도 실패로 잡습니다. **자사 도메인의 401/403은 기본 실패**이며 예외는 `AUTH_GATED` 에 엔드포인트 + 메서드로 명시한 것만 인정합니다(정규식으로 넓게 허용하면 실제 결함이 '인증 게이트'로 흡수돼 미탐). 2026-07-31 실측 기준 401/403을 내는 엔드포인트가 없어 **현재 `AUTH_GATED` 는 비어 있습니다.** 외부 링크는 INFO로 기록만 남깁니다
- **헬스체크 요청 식별**: 자사 도메인 요청에만 상수 헤더 `X-Ezlab-Healthcheck: 1` 을 붙여 서버 로그·APM에서 실사용자 트래픽과 분리합니다. 런마다 바뀌는 실행 ID는 요청에 싣지 않습니다(CloudFront 캐시 키 분산 우려 — `report-status.json` 의 `runId` 로만 남기고 시각으로 대조)
- **분석·광고 beacon 차단**: 렌더마다 나가던 GA4 수집·광고 전환 요청을 차단해 통계 오염을 막습니다(48런/일 규모, GitHub 러너는 IP가 유동적이라 GA4 IP 필터로 거를 수 없음). 렌더에 관여하는 로더(gtag.js/gtm.js)와 SDK는 통과시킵니다
- **전체 재시도 없음**: 오류 1건에 9개 STEP이 통째로 다시 돌면 서버가 불안정한 시점에 요청이 두 배가 됩니다. 오탐 방어는 아래 실패 경로 재시도와 장애 지문으로 대체했습니다
- **실패 경로 재시도 정책(2026-08-01 개편)**: 전체 실행에 고정 지연을 더하지 않고 **실패한 요청에만** 점진 백오프(2초 → 4초)를 붙입니다.
  - **4xx는 즉시 확정**(재시도 없음). 예외는 '지연 404' 하나 — 오리진 간헐 장애의 실측 시그니처에 한해 **자사 호스트 + 멱등 GET + 응답 8초 이상**을 모두 만족할 때만 타임아웃 계열로 취급합니다.
  - **5xx·응답없음(0)·타임아웃은 재시도**: 링크·네비게이션·API는 최대 3회(2s→4s), STEP1 본측정·크롤 네비·term 페이지·이미지·설치 파일 Range 프로브는 2초 후 1회.
  - **STEP1 워밍업 실패는 판정에서 제외**하고 본측정 3회로만 판단합니다. 본측정 중 확정 실패가 나오면 남은 샘플을 끊습니다(전면 장애 시 STEP1이 전체 예산을 소진하는 것 방지 — 언어당 최악 146초 → 62초).
  - **인증서 점검은 순수 연결 타임아웃만 1회 재시도**합니다. 만료·호스트 불일치는 확정 상태라 즉시 판정합니다.
  - **재시도 회복은 INFO**(스코어 미반영), 최종 실패는 WARN/FAIL 그대로입니다.
  - **재시도 예산 게이트**: 재시도 전에 [경과 + 백오프 + timeout]이 `REPORT_SAFETY_MS`(510초) 안에 끝나는지 확인하고, 부족하면 최초 실패로 확정하며 `retrySkipped: 'budget'` 을 남깁니다. 510~600초 구간은 증거 생성·리포트 저장 여유로 보존합니다. **다만 이 게이트는 재시도 경로만 통제하며 리포트 저장을 보장하지 않습니다** — 최초 요청·스크린샷 같은 다른 `await` 가 멈추면 전체 타임아웃까지 끌려갑니다.
  - **DOM 이미지 locator 방어**: `<img src>` 읽기는 호출당 2초 제한. 타임아웃 시 같은 언어의 남은 순회를 중단해 `이미지 수 × timeout` 증폭을 막고, 사이트 FAIL로 단정하지 않고 **WARN + `coverageComplete: false`** 로 남긴 뒤 다음 언어를 계속 실행합니다.
- **장애 지문**: `report-status.json` 의 `failFingerprints` 에 `호스트+경로|오류계열` 지문을 남깁니다(쿼리 제외). 계산은 **`scripts/fail_streak.py` 한 곳**에 있고 Slack 알림과 GitHub 이슈 게이트가 이를 공유합니다.
  - 판정은 **누적 교집합**입니다. `{A,B} → {A} → {B}` 처럼 장애가 갈아타면 연속이 끊깁니다.
  - **지문 이력이 없으면 횟수 기준으로 폴백**합니다 — 판정 불가 상황에서 게이트를 걸면 실제 장애 알림이 통째로 죽습니다.
  - 복구 알림도 같은 기준을 쓰되 **직전 런의 지문은 이력에서 읽습니다**(현재 런이 PASS면 지문이 비어 있어 폴백으로 새기 때문).
- **네트워크 실패 판정**: `requestfailed` 는 두 단계로 거릅니다.
  1. **우리가 차단한 요청은 `WeakSet<Request>` 기록으로 제외**합니다. 오류 문자열로는 구분되지 않고(`route.abort()` 기본값이 `failed`), URL Set이 아닌 Request 객체로 기록해야 같은 URL의 진짜 실패를 오인하지 않습니다.
  2. 남은 실패는 **실제 네트워크 오류 허용 목록**(`ERR_FAILED`, `ERR_NAME_NOT_RESOLVED`, `ERR_CONNECTION_*`, `ERR_TIMED_OUT`, `ERR_CERT_*`, `ERR_SSL_*` 등)으로만 인정합니다. 브라우저가 스스로 취소한 `ERR_ABORTED` 는 장애가 아닙니다(이 단계 도입 전 `_next/image` 오탐 8건 발생). 차단 목록이 아니라 허용 목록인 이유는 모르는 오류를 장애로 올리지 않기 위해서입니다.
- **증거 수집**: 모든 FAIL·WARN에 시각 증거를 보장합니다.
  - 기록은 **`recordIssue()` 단일 진입점**을 거칩니다. 검사 항목이 추가돼도 지문 계산과 증거 확보가 자동으로 따라옵니다.
  - **화면으로 확인되는 장애**(UI·콘텐츠·로그인·다운로드 버튼·DOM 이미지·크롤·이지다운)는 발견 즉시 그 페이지를 촬영합니다.
  - **화면에 나타나지 않는 장애**(API·설치 파일·SSL·OG 메타 이미지·네트워크 실패·예산 초과)는 별도 페이지 `setContent()` 로 렌더한 **진단 카드**로 남깁니다. STEP·유형·심각도·URL·HTTP 상태·증상·언어·시각·응답 시간·`Content-Type`·`Content-Range`·네트워크 오류·실행 ID를 싣고, 이미지 실패는 참조 페이지·응답 크기·선별 헤더(`server`, `via`, `x-cache`, `x-amz-cf-*`)와 텍스트 오류 본문 발췌를 더합니다(민감 헤더·바이너리 제외, 추가 네트워크 요청 없음).
  - **지문당 파일 1장을 공유**하되 모든 기록에 `evidencePath` 가 채워집니다. 리포트 저장 직전 최종 보완이 돌며, 결과는 `evidenceMissing` 필드로 확인합니다(0이어야 정상).
  - 각 기록에 `evidenceType`(`page`/`element`/`diagnostic`) · `evidencePath` · `evidenceError` 를 담고 Playwright HTML 리포트에도 첨부합니다. INFO 등급 외부 링크는 증거 필수 대상에서 제외합니다.
- **점검 완주 여부**: 시간 예산으로 STEP을 건너뛰면 WARN이 되고, `coverageComplete: false` 와 `skippedSteps` 를 함께 내려 '전 항목 정상'과 '일부 미점검'을 구분합니다
- **자동 리포팅**: PASS/FAIL/WARN/SLOW/INFO 카운터 집계 + 장애 리포트(개발팀 전달용) 자동 생성
- **실패 알림**: FAIL 시 GitHub Issue 자동 생성(열린 이슈가 있으면 코멘트만 추가) + Slack 알림(신규/지속/복구). Slack 발송은 일시적 오류에 백오프 재시도(최대 4회)

### 지표 4종 (2026-08-02 개편)

예전에는 `PASS / (PASS+WARN+FAIL)` 하나를 "Health Score"로 썼습니다. WARN과 FAIL을 구분하는 항이 없어 **탐지 범위를 넓힐수록 가동률이 떨어지는 구조**였고, OG 이미지 403 검사를 추가한 직후 8월 가동률이 0%로 표시됐습니다. 성격이 다른 질문 넷으로 분리했습니다(산식 `scripts/dashboard_metrics.py`, 규칙 테스트 `scripts/test_dashboard_metrics.py`).

| 지표 (화면 표기) | 산식 | 설명 |
|---|---|---|
| **최근 서비스 정상률** | `가용 / (가용 + 장애)` | FAIL → 장애, PASS·완주 WARN → 가용, 미완주 WARN·UNKNOWN → **확인 불가**(분모 제외, 건수는 카드에 표시) |
| **점검 완료율** | `완주 실행 / 완주 여부를 아는 실행` | 헬스체크 자체의 건강 지표. 표본 10건 미만이면 `데이터 부족` |
| **무경고 실행률** | `PASS / (PASS+WARN+FAIL)` | 기존 Health Score와 같은 산식. 검사를 추가하면 낮아지는 것이 정상 |
| **확인이 필요한 항목** | 지문 단위 중복 제거한 미해결 결함 수 | 완주 실행에서 2회 연속 미검출이면 해결 전환, 미완주 실행은 해결 판정에서 제외 |

품질 경고를 장애로 세지 않는 것이 핵심입니다. `coverageComplete` 기록이 없는 과거 런의 WARN도 임의로 가용 처리하지 않고 확인 불가로 둡니다.

- **현재 서비스 표시**: `FAIL → 장애 감지` / `UNKNOWN·미완주 → 점검 결과 확인 필요` / `완주 WARN·PASS → 정상 운영 중`
- **최근 24시간 장애**: 최근 24시간 내 FAIL 건수
- **서버 첫 응답(TTFB) 추이**: 언어별 스파클라인, 최근 24회 · 위험 임계치 500ms. 응답 헤더까지만 측정해 본문 다운로드 시간을 제외(워밍업 1회 후 3회 중앙값)
- **SSL 인증서 만료**: 도메인별 남은 일수(D-day)와 만료일 미터(경고 D-14 / 장애 D-7). 정상일 때도 항상 노출
- **일별 가동률(최근 90일)**: 날짜별 PASS/WARN/FAIL 히트맵
- **월별 요약**: 서비스 가용률 도넛(영구 보존). 확인 불가가 분모에서 빠지므로 **세그먼트 비율과 가운데 숫자는 일부러 다릅니다**
- **실행 목록**: 월·일 아코디언 + PASS/WARN/FAIL 필터. 펼치면 응답시간, cURL 재현 명령어, 장애 상세, 개별 Playwright 리포트 링크

### 판정 등급

**이지랩이 고칠 수 있는 문제만 스코어에 반영**합니다.

| 등급 | 스코어 반영 | 런 상태 | 해당 사례 |
|---|:---:|---|---|
| **FAIL** | O | FAIL | 서버/API 응답 이상(404·5xx), 점검 페이지 노출, 로그인 페이지 진입 실패, 인증서 D-7 이하 |
| **WARN** | O | WARN | 이미지 로드 실패, 다운로드 버튼 미감지, 로그인 버튼 누락, 크롤 렌더 실패, 인증서 D-14 이하, 오리진 간헐 불안정 |
| **SLOW** | X | 영향 없음 | 응답 3초 초과 — 느릴 뿐 정상 응답이므로 정보성 지표로만 집계 |
| **INFO** | X | 영향 없음 | 외부 링크(제3자 도메인) 이상, **재시도 후 회복된 간헐 실패** |

- **INFO를 빼는 이유**: 외부 링크는 이지랩이 소유·수정할 수 없는 서버입니다. 깨진 링크는 대시보드에 `참고 항목`으로 계속 노출됩니다.
- **간헐 회복**: 개별 기록은 항상 INFO로 남기고, 한 런에서 **서로 다른 정규화 지문이 2종 이상** 회복될 때만 `오리진 간헐 불안정` WARN 1건으로 승격합니다(같은 경로의 blip이 4개 언어에서 반복되는 것과 구분).

### 집계 마이그레이션 (첫 운영 실행 전 1회 필수)

월별·일별 집계에 서비스 분류 벡터(`avail`/`outage`/`indet`)가 추가됐습니다. 일부 월에만 벡터가 있는 부분 마이그레이션 상태를 정상 데이터로 읽으면 백필 전 월이 0%로 표시됩니다.

```bash
git fetch origin gh-pages
python3 scripts/backfill_stats.py /tmp        # 전 구간 재구성 + stats-meta.json 생성
# 산출물을 gh-pages 루트에 반영: monthly-stats.json / daily-stats.json / coverage.json / stats-meta.json
```

- 백필은 3단계로 검증하며 위반 시 **파일을 쓰지 않고 종료 코드 1로 중단**합니다: ① 재구성 결과(병합 전)에 `avail + outage + indet` = 읽은 실행 수 ② 병합 결과의 형태(세 키 존재·음수 없음) ③ 벡터를 교체한 구간만 병합 후 합계 재검증. 합계 검증을 병합 결과 전체에 걸면 prune된 구간에서 오탐이 납니다.
- `stats-meta.json` 에 `schemaVersion: 2` 와 `backfillComplete: true` 가 **둘 다** 있을 때만 대시보드가 벡터를 신뢰하고, 없으면 전 구간 보수적 환산(WARN = 확인 불가)으로 통일합니다.
- 재구성이 더 적은 실행을 본 구간에서는 기존 벡터를 통째로 보존합니다(항목별 `max` 로 섞지 않음).
- **동일 실행 ID 재처리(upsert)**: 같은 `YYYY-MM-DD_HH-MM` 키가 다시 들어오면 이전 분류를 빼고 새 분류를 더합니다. 단 `statuses.json` 은 최근 500건만 유지하므로 그보다 오래된 런은 백필로 재구성해야 합니다.

### 판정 규칙 테스트 (`tests/judgment.spec.ts`)

헬스체크 본체는 실제 사이트 상태에 따라 결과가 달라져서 판정 로직 검증에 쓸 수 없습니다(운영 결함이 고쳐지면 '그 결함을 잡는지' 확인할 방법이 사라짐). **규칙은 운영 상태와 무관하게 여기서 고정**합니다.

| 영역 | 확인 내용 |
|---|---|
| HTTP 상태 판정 | 2xx·3xx 정상 / 400·404·405·408·429·5xx·응답없음 실패 / 공개 경로 401·403 실패 |
| 이미지 판정 | `Content-Type: image/*`, 200인데 HTML·XML 본문, 본문 크기 0, 206의 `Content-Range` 유효성 |
| 설치 파일 Range 프로브 | 206 + `bytes 0-0/N` + 수신 바이트 정확히 1일 때만 통과, Range 무시(200) 처리 |
| 네트워크 실패 | 실제 오류는 장애, 브라우저 자체 취소(`ERR_ABORTED`)·차단·사유 없음은 무시 |
| 장애 지문 | 쿼리 무시, 오류 계열 구분, 콘텐츠 누락 분류 |
| 증거 수집 | FAIL·WARN 증거 필수·INFO 제외, 지문당 파일 1장 공유, 생성 실패 시 `evidenceError`, 보완 후 누락 0건 |

연속 판정은 `scripts/test_fail_streak.py` 가 검증합니다 — 누적 교집합(`{A,B}→{A}→{B}`), A→B 억제, 지문 이력 부재 시 폴백, 복구 알림 시퀀스(A→B→PASS 억제 / A→A→PASS 발송).

**두 테스트 모두 CI에서 헬스체크보다 먼저 실행되며, 실패하면 런이 중단됩니다.**

Slack 알림은 `DRY_RUN=1` 로 발송 없이 미리보기할 수 있습니다.

```bash
DRY_RUN=1 SLACK_WEBHOOK_URL=x HEALTH_STATUS=FAIL RECENT_STATUSES=FAIL,PASS \
  RUN_DATETIME=2026-07-31_00-47 python3 scripts/notify_slack.py
```

### 아직 검증되지 않은 것

- **CI 환경 미실행** — 러너 지역·네트워크가 로컬과 달라 실행 시간, 간헐 실패 빈도, `ERR_ABORTED` 패턴이 다를 수 있습니다. 운영 반영 전 브랜치에서 `workflow_dispatch` 수동 실행을 권장합니다.
- **변경 전후 요청량·실행시간 A/B** — 비교는 CI 런끼리, 같은 job 안에서 전후를 연속 실행해야 의미가 있습니다(로컬은 거리·throttling으로 기준선이 안 됨). `.github/workflows/ab-network-policy.yml` 이 수행하며 **참고 리포트가 아니라 게이트**입니다.

  | 검사 | 실패 조건 |
  |---|---|
  | 리포트 생성 | 각 조건 실행 후 `report-status.json` 없음 |
  | 표본 수 | `off`/`on` 결과 개수가 `repeats` 와 불일치 |
  | 점검 완주 | 어느 런이든 `coverageComplete !== true` |
  | 증거 누락 | 어느 런이든 `evidenceMissing !== 0` |
  | 실행 시간 | 어느 런이든 8.5분(510초) 예산 초과 |
  | 요청 증가 | 브라우저 자사 요청 중앙값 증가가 임계(기본 +10%) 초과 |

  실행 전 매번 `report-status.json` 을 지우고(직전 조건 결과 복사로 인한 오염 방지), 조건 순서는 회차마다 뒤집습니다(CDN 워밍이 조건과 결합되는 것 방지).

  **실행 순서** — `workflow_dispatch` 는 워크플로 파일이 default branch(main)에 있어야 트리거됩니다.
  1. 작업 브랜치 푸시
  2. A/B 워크플로 파일만 main 에 먼저 반영 (스케줄 트리거가 없어 운영 동작은 그대로)
  3. `gh workflow run ab-network-policy.yml --ref <브랜치> -f repeats=3`
  4. 게이트 통과 확인 후 나머지 변경을 main 에 병합

  브랜치 CI 성공은 A/B 통과가 아닙니다.
- **요청 계측 범위** — `requestCounts.own`/`third` 는 브라우저가 낸 요청만 셉니다(`scope: 'browser-only'`). `page.request` 검증, `measureTTFB` 의 raw HTTPS, 인증서 TLS 핸드셰이크는 제외됩니다. `HC_NET_POLICY=off` 도 브라우저 라우팅 헤더와 beacon 차단만 해제합니다.
- **CloudFront 캐시 정책 미확인** — `ezlab.im` 정적 자산이 GET·HEAD 모두 반복 MISS로 관측됐으나 원인 미확정입니다. 이 때문에 식별 헤더는 상수 하나만 보냅니다.

### 유지보수 스크립트

집계 파일이 손상됐거나 판정 기준이 바뀌었을 때 씁니다. 둘 다 gh-pages 체크아웃을 대상으로 동작하므로 작업 전용 워크트리에서 실행하세요.

```bash
# gh-pages 작업본 준비
git fetch origin gh-pages
git worktree add /tmp/ghp origin/gh-pages --detach

# 집계 파일 재구성 (statuses / perf / daily / monthly) — 손상·유실 복구용
python3 scripts/backfill_stats.py /tmp/ghp

# 판정 기준 변경에 맞춰 과거 WARN 정정 — 반드시 dry-run으로 먼저 확인
python3 scripts/reclassify_warns.py /tmp/ghp            # 검토만 (파일 변경 없음)
python3 scripts/reclassify_warns.py /tmp/ghp --apply    # 실제 반영

# 확인 후 커밋·푸시
cd /tmp/ghp && git add -A && git commit -m "..." && git push origin HEAD:gh-pages
git worktree remove /tmp/ghp
```

> `reclassify_warns.py` 는 루트 집계뿐 아니라 **개별 실행 폴더의 `status.json` 도 함께 정정**합니다. 루트만 고치면 다음 백필 때 낡은 판정이 되살아납니다. 멱등이라 두 번 실행해도 결과가 같습니다.
