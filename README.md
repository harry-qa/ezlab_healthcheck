# Playwright 기반 이지랩(ezLab) 서비스 헬스 체크 자동화

본 프로젝트는 [이지랩(ezLab)](https://ezlab.im) 서비스의 배포 후 안정성을 신속하게 검증하기 위해 구축된 하이브리드 자동화 도구입니다.

## 1. 개요

이지랩 전체 서비스(이지캡쳐, 이지집, 이지파인더, 이지메모, 이지캠, 이지리더)를 대상으로 서버 생존, API 응답, UI 링크 연결, 다운로드 페이지, 콘텐츠 무결성, 이미지 로딩, 로그인 폼을 다국어(ko/en/jp/tw) 환경에서 통합 점검합니다. 기존의 수동 점검 방식에서 벗어나 QA 공수를 절감하고 배포 품질을 확보하는 것을 목적으로 합니다.

## 2. 점검 항목 (8단계)

### STEP 1 · 다국어 서버 생존 확인
- `ezlab.im/ko`, `/en`, `/jp`, `/tw` 각 언어별 메인 페이지의 HTTP 상태 코드를 확인하여 서버 생존 여부를 즉각 판별합니다.

### STEP 2 · API 자동 수집 및 검증
- 각 언어 페이지를 탐색하면서 네트워크 인터셉트(XHR/Fetch)를 통해 내부 API 호출을 자동 수집하고, 상태 코드(4xx/5xx)를 검증합니다.

### STEP 3 · UI 링크 전수조사
- 홈페이지에서 수집한 내부 링크를 **depth 2**까지 재귀 탐색하여 누락 페이지 없이 전수 조사합니다.
- `<a>` 태그뿐 아니라 **탭 버튼 클릭으로 전환되는 페이지**(예: 이용약관 탭 구조)도 자동 감지합니다.
- `mailto:`, `.exe/.apk/.zip` 등 다운로드 파일 링크는 크롤링에서 제외합니다.
- 응답 3초 초과 시 SLOW로 분류하며, 콘텐츠 내 에러 키워드("점검중", "404 not found" 등)도 감지합니다.

### STEP 4 · 서비스별 다운로드 페이지 직접 검증
- 각 서비스(이지캡쳐~이지리더)의 개별 다운로드 페이지에 직접 진입하여 페이지 응답 상태와 다운로드 버튼(.exe/.apk/.zip) 존재 여부를 확인합니다.

### STEP 5 · 언어별 핵심 콘텐츠 무결성 확인
- 언어별 메인 페이지에서 핵심 키워드(ko: "다운로드", "이지캡쳐" 등 / en: "download", "ezcapture" 등 / jp: "ダウンロード" 등 / tw: "下載" 등)의 존재 여부를 검증하여 콘텐츠 누락을 감지합니다.

### STEP 6 · 깨진 이미지 감지
- 언어별 페이지의 모든 `<img>` 태그를 순회하여 이미지 로드 실패(4xx/5xx)를 감지합니다.
- CDN 장애 또는 경로 오류로 인한 이미지 깨짐을 자동으로 탐지합니다.

### STEP 7 · 로그인 폼 렌더링 확인
- 로그인 페이지 진입 후 카카오 / 네이버 / 구글 소셜 로그인 버튼의 렌더링 여부를 확인합니다.
- 인증 연동 장애를 조기에 감지합니다.

### STEP 8 · 이지다운(ezdown.kr) 정보 페이지 점검
- 이지다운은 **별도 도메인(`ezdown.kr`)** 의 앱 소개 + 사용 후기 + FAQ 정보성 페이지입니다(다운로드/로그인 기능 없음).
- Next.js SPA 특성상 단순 HTTP 200으론 판별이 안 되므로, 언어별(ko/en/jp/tw) **실제 렌더 후 타이틀·본문·핵심 콘텐츠(후기/FAQ)** 존재를 검증합니다.
- 이미지는 lazy-load 오탐을 피하기 위해 DOM이 아닌 **URL 응답 상태**로 깨짐을 판별합니다.

## 3. 주요 특징

- **다국어 통합 점검**: 한국어, 영어, 일본어, 중국어(번체) 4개 언어를 단일 테스트에서 순회
- **하이브리드 검증**: 서버 응답 + API 인터셉트 + UI 링크 크롤링 + 콘텐츠 검증 + 이미지/로그인 점검을 한 번에 수행
- **WAF 회피**: 일반 브라우저와 동일한 `User-Agent` 헤더 적용 및 랜덤 딜레이(300ms~800ms) 로직 구현
- **자동 리포팅**: 테스트 결과를 PASS/FAIL/WARN 카운터로 집계하고 장애 리포트(개발팀 전달용) 자동 생성
- **실패 알림**: FAIL 감지 시 GitHub Issue 자동 생성 + **Slack 알림**(정상→FAIL / FAIL→복구 *전환 시에만* 발송 → 장애 지속 중 스팸 없음)
- **네트워크 오류 대응**: CI 환경에서 일시적 오류에 대해 1회 자동 재시도

## 4. 헬스체크 대시보드

GitHub Pages에서 누적 실행 이력을 다크모드 대시보드로 확인할 수 있습니다.

👉 **https://harry-qa.github.io/ezlab_healthcheck/**

- **Health Score**: 최근 실행 기준 PASS 비율(%)
- **현재 시스템 상태 / 최근 24시간 장애**: 최신 실행 상태와 최근 24시간 내 FAIL 건수
- **서버 첫 응답(TTFB) 추이**: 언어별(ko/en/jp/tw) 스파클라인, 최근 24회 · 위험 임계치 **500ms** (평균·최대·현재값 표기)
  - 응답 헤더(첫 바이트)까지만 측정해 본문 다운로드 시간을 제외(워밍업 1회 후 3회 중앙값). 서버 처리 체감에 가깝고, CI 러너↔서버 거리·본문 크기에 덜 흔들립니다.
- **일별 가동률(최근 90일)**: 날짜별 PASS/WARN/FAIL 히트맵
- **월별 요약**: 월별 가용률 도넛 차트(영구 보존)
- **실행 목록**: 월·일 아코디언 + PASS/WARN/FAIL 필터. 각 실행을 펼치면 서버 응답시간, cURL 재현 명령어, 장애 상세, 개별 Playwright 리포트 링크 확인

## 5. 자동 실행 · 데이터 보존 · 알림

- **실행 주기**: GitHub Actions 스케줄(매시 정각, `0 * * * *`) + 수동 실행(`workflow_dispatch`)
  > GitHub 무료 플랜 특성상 일부 정시 실행은 지연/누락되어, 실제로는 하루 수 회~십수 회 수준으로 기록됩니다.
- **데이터 보존**
  - 실행 목록 / 응답시간 / 장애 상세: 최근 **500회** 롤링 (약 2.5개월)
  - 월별 요약 · 90일 히트맵: 누적 집계로 **영구 보존** (폴더 정리와 무관)
  - 개별 Playwright 리포트 폴더: **120일** 경과분 자동 삭제 (GitHub Pages 1GB 한도 방어)
- **알림**
  - FAIL 감지 시 GitHub Issue 자동 생성
  - 정상→FAIL / FAIL→복구 **전환 시** Slack 알림 (전환 기준이라 장애 지속 중 스팸 없음)
  - Slack 웹훅은 `SLACK_WEBHOOK_URL` 시크릿으로 설정, **Slack 연동 테스트** 워크플로우로 검증 가능

## 6. 기술 스택

- **Language**: TypeScript
- **Framework**: Playwright
- **Runtime**: Node.js
- **CI/CD**: GitHub Actions
- **Report Hosting**: GitHub Pages

## 7. 실행 방법

```bash
# 의존성 설치
npm install

# Playwright 브라우저 설치
npx playwright install

# 테스트 실행
npx playwright test

# HTML 리포트 확인
npx playwright show-report
```
