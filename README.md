# Playwright 기반 이지랩(ezLab) 서비스 헬스 체크 자동화

본 프로젝트는 [이지랩(ezLab)](https://ezlab.im) 서비스의 배포 후 안정성을 신속하게 검증하기 위해 구축된 하이브리드 자동화 도구입니다.

## 1. 개요

이지랩 전체 서비스(이지캡쳐, 이지집, 이지파인더, 이지메모, 이지캠, 이지리더)를 대상으로 서버 생존, API 응답, UI 링크 연결, 다운로드 페이지·파일, 콘텐츠 무결성, 이미지 로딩, 로그인 폼, SSL 인증서 만료를 다국어(ko/en/jp/tw) 환경에서 통합 점검합니다. 기존의 수동 점검 방식에서 벗어나 QA 공수를 절감하고 배포 품질을 확보하는 것을 목적으로 합니다.

## 2. 점검 항목 (9단계)

### STEP 1 · 다국어 서버 생존 확인
- `ezlab.im/ko`, `/en`, `/jp`, `/tw` 각 언어별 메인 페이지의 HTTP 상태 코드를 확인하여 서버 생존 여부를 즉각 판별합니다.

### STEP 2 · API 자동 수집 및 검증
- 각 언어 페이지를 탐색하면서 네트워크 인터셉트(XHR/Fetch)를 통해 내부 API 호출을 자동 수집하고, 상태 코드(4xx/5xx)를 검증합니다.

### STEP 3 · UI 링크 전수조사
- 홈페이지에서 수집한 내부 링크를 **depth 2**까지 재귀 탐색하여 누락 페이지 없이 전수 조사합니다.
- `<a>` 태그뿐 아니라 **탭 버튼 클릭으로 전환되는 페이지**(예: 이용약관 탭 구조)도 자동 감지합니다.
- `mailto:`, `.exe/.apk/.zip` 등 다운로드 파일 링크는 크롤링에서 제외합니다.
- 응답 3초 초과 시 SLOW로 분류합니다. 점검 페이지 신호("점검중", "서비스 준비중") 감지는 **내부 링크에 한정**하며(외부 링크 콘텐츠로 인한 오탐 방지), 스크립트/스타일 번들에 실린 문구는 제외하고 실제 마크업만 검사합니다.

### STEP 4 · 서비스별 다운로드 페이지 검증
- STEP 3에서 자동 수집한 각 서비스 도구 페이지(`/ko/tool/*`)에 직접 진입하여 페이지 응답 상태와 다운로드 버튼(.exe/.apk/.zip) 존재 여부를 확인합니다.

### STEP 4-1 · 실제 설치 파일 URL 검증
- 설치 파일 URL은 **`/api/tools/info`** 에서 수집합니다. 다운로드가 JS 기반이라 페이지의 `a[href*=".exe"]` 로는 한 건도 잡히지 않아, 과거 이 검사는 **커버리지 0인 채로 통과**하고 있었습니다.
- 수집한 URL을 **HEAD**로 확인하고(200/206 기대), HEAD를 막는 CDN(403/405)만 **Range GET(앞 1바이트)** 으로 재확인합니다.
- Range 재확인은 `page.request.get`(본문 전체 버퍼링)이 아니라 **스트리밍 요청**을 씁니다. 헤더 수신 시점에 206이 아니면 즉시 연결을 끊어, 서버가 Range를 무시할 때 설치 파일 전체를 내려받는 것을 막습니다. 206이어도 `Content-Range` 형식과 **수신 바이트가 정확히 1바이트인지**까지 확인합니다 — 2바이트 이상이면 서버가 Range를 지키지 않은 것이라 '앞 1바이트만 받았다'는 전제가 깨집니다.
- 파일 URL을 **한 건도 수집하지 못하면 WARN**으로 남깁니다 — 커버리지 0을 조용히 통과시키지 않습니다.
- 설치 파일 응답 이상은 다운로드 기능 자체가 죽은 것이므로 **FAIL**입니다.

### STEP 5 · 언어별 메인 페이지 통합 점검 (콘텐츠 + 이미지)
- 언어별 메인 페이지에서 핵심 키워드(ko: "다운로드", "이지캡쳐" 등 / en: "download", "ezcapture" 등 / jp: "ダウンロード" 등 / tw: "下載" 등)의 존재 여부를 검증하여 콘텐츠 누락을 감지합니다.
- SPA 특성상 진입 직후 본문이 비어 있을 수 있어, **재시도 진입 + 본문 렌더 대기** 후 판정하여(STEP 8과 동일) 순간 지연·하이드레이션으로 인한 오탐을 방지합니다.
- **콘텐츠와 이미지를 한 번의 방문에서 함께 점검합니다.** 예전에는 메인 페이지를 STEP2·3·5·6이 각각 렌더해 언어당 4번 방문했습니다(렌더 1회가 자사 요청 100건대). 로그인·도구 페이지는 URL이 달라 통합 대상이 아닙니다.

### STEP 6 · 깨진 이미지 감지 (3계층)
STEP 5의 방문에서 세 경로로 수집하고, STEP 6에서는 자산 단위로 판정만 합니다.

1. **OG / Twitter 메타 이미지** — `meta[property="og:image"]`, `meta[name="twitter:image"]`. DOM `<img>` 에 잡히지 않아 기존 검사가 통째로 놓치던 경로이며, 카카오톡·슬랙 공유 썸네일이 여기에 달려 있습니다.
2. **브라우저가 실제 요청한 이미지** — `resourceType() === 'image'` 인 응답과 `requestfailed` 를 한 쌍으로 관찰해 CSS 배경·`srcset`·preload를 커버합니다. 브라우저가 실제로 선택·요청한 자산만 검증하며, 모든 CSS 규칙과 모든 `srcset` 후보를 검증하지는 않습니다.
3. **DOM `<img src>`** — 네트워크로 요청되지 않은 지연 로딩 이미지를 보완합니다.

판정 규칙:

| 관측 | 처리 |
|---|---|
| 네트워크에서 4xx·5xx | 캐시 여부와 무관하게 사용자가 실패 응답을 받은 것 → 즉시 실패, 능동 재요청 없음 |
| 네트워크에서 200만 관측 | 브라우저 캐시 히트일 수 있어(컨텍스트가 STEP2부터 재사용됨) **요청 URL당 1회 능동 검증** |
| 능동 검증 200/206 | 상태 + **`Content-Type: image/*`** + **본문 크기 > 0** 까지 확인 (200인데 XML 오류 본문을 주는 경우가 실재). 206은 **`Content-Range` 형식**도 함께 확인 |
| 304 | 정상 재검증. 본문이 없는 것이 정상이라 크기·타입 검사 대상 아님 |
| `requestfailed` | 우리가 차단한 beacon은 `WeakSet<Request>` 로 제외하고, 남은 것 중 **실제 네트워크 오류만** 실패로 인정 (아래 '네트워크 실패 판정' 참고) |
| 제3자 도메인 | 장애 점수에서 제외 |

- 집계는 **원본 자산 URL**, 판정과 능동 검증 완료 여부는 **실제 요청 URL** 기준입니다. Next 이미지 프록시는 폭(`w=32`/`w=3840`)마다 URL이 달라 특정 폭만 실패할 수 있기 때문입니다.
- 결함 기록은 자산당 1건이며 **참조 언어와 사용처(og:image/twitter:image)** 를 함께 남깁니다. 언어별로 같은 WARN을 복제하지 않습니다.
- 네트워크 관찰 구간은 고정입니다: 진입 `domcontentloaded`(15초) → `load` 최대 3초 → 안정화 1초 → 핸들러 해제. `networkidle` 은 쓰지 않습니다(자산 하나가 안 끝나면 타임아웃까지 통째로 날립니다).

### STEP 7 · 로그인 폼 렌더링 확인
- 로그인 페이지가 열리고 소셜/이메일 로그인 버튼이 **화면에 렌더되는지**를 언어별로 확인합니다(ko: 카카오·네이버·구글·이메일 / en·jp·tw: 구글·이메일). 버튼 누락은 WARN, 페이지 진입 실패는 FAIL.
- **로그인 "입구"의 렌더링 점검**입니다. 버튼이 안 떠 있으면 provider SDK 로드 실패·키 누락·UI 회귀 등의 조기 신호일 수 있어, 사용자 신고 전에 알아채는 것이 목적입니다.
- **검증 범위 밖**: 버튼 클릭 이후의 실제 OAuth 로그인 성공 여부(토큰 교환, 카카오/네이버/구글 provider 서버 상태)는 점검하지 않습니다. 즉 "버튼이 정상 노출되는가"까지만 보장하며, 실제 로그인 가능 여부를 보장하지는 않습니다.

### STEP 8 · 이지다운(ezdown.kr) 정보 페이지 점검
- 이지다운은 **별도 도메인(`ezdown.kr`)** 의 앱 소개 + 사용 후기 + FAQ 정보성 페이지입니다(다운로드/로그인 기능 없음).
- Next.js SPA 특성상 단순 HTTP 200으론 판별이 안 되므로, 언어별(ko/en/jp/tw) **실제 렌더 후 타이틀·본문·핵심 콘텐츠(후기/FAQ)** 존재를 검증합니다.
- 이미지는 lazy-load 오탐을 피하기 위해 DOM이 아닌 **URL 응답 상태**로 깨짐을 판별합니다.

### STEP 9 · SSL 인증서 만료 점검
- `ezlab.im` / `ezdown.kr` 두 도메인의 SSL 인증서 만료일을 TLS 핸드셰이크로 직접 확인합니다.
- 인증서 만료는 전 서비스 동시 중단을 부르므로 **사전 경고**가 목적입니다: 만료까지 **D-14 이하 → WARN**(대시보드 조기 경고), **D-7 이하 또는 만료됨 → FAIL**(자동갱신 실패 신호로 보고 Slack·이슈 알림).

## 3. 주요 특징

- **다국어 통합 점검**: 한국어, 영어, 일본어, 중국어(번체) 4개 언어를 단일 테스트에서 순회
- **하이브리드 검증**: 서버 응답 + API 인터셉트 + UI 링크 크롤링 + 콘텐츠 검증 + 이미지/로그인 점검을 한 번에 수행
- **WAF 회피**: 일반 브라우저와 동일한 `User-Agent` 헤더 적용 및 랜덤 딜레이(300ms~800ms) 로직 구현 — 딜레이는 링크 검증 요청에만 적용되며 렌더·이미지·API에는 별도 스로틀이 없습니다
- **통합 HTTP 판정**: 공개 경로는 2xx·3xx만 정상으로 봅니다. 400·405·408·429는 예전에 PASS로 새던 구멍이었습니다. **자사 도메인의 401/403은 기본적으로 실패**이며, 예외는 `AUTH_GATED` 에 엔드포인트 + 메서드로 명시한 것만 인정합니다. 경로 묶음을 정규식으로 넓게 허용하면 실제로는 200이어야 할 페이지가 403으로 망가져도 '인증 게이트'로 흡수돼 미탐이 됩니다.
  - **현재 `AUTH_GATED` 는 비어 있습니다.** 2026-07-31 실측 기준 비로그인 GET 응답이 `/ko/login` 200 · `/en/login` 200 · `/api/auth/me` 200 · `/ko/point` 307 · `/ko/mypage` 307 · `/ko/profile`·`/ko/order`·`/ko/payment`·`/api/user`·`/api/point`·`/api/order` 404 로, **401/403을 내는 엔드포인트가 하나도 없습니다.** 실제 런에서도 ezlab.im 응답 중 401/403은 0건이었습니다(403은 전부 CDN 자산 결함).
  - 항목을 추가할 때는 반드시 실측한 엔드포인트·메서드·비로그인 기대 상태를 근거로 적습니다.
  - 외부 링크는 종전대로 INFO로 기록만 남기고 스코어에 반영하지 않습니다
- **헬스체크 요청 식별**: 자사 도메인 요청에만 상수 헤더 `X-Ezlab-Healthcheck: 1` 을 붙여 서버 로그·APM에서 실사용자 트래픽과 분리할 수 있게 합니다. 제3자 도메인에는 붙이지 않습니다. **런마다 바뀌는 실행 ID는 요청에 싣지 않습니다** — CloudFront 캐시 키에 요청 헤더가 포함된 설정이면 30분마다 캐시가 갈려 오리진 부하를 키울 수 있고, 현재 그 정책이 미확정이기 때문입니다(실행 ID는 `report-status.json` 의 `runId` 로만 남기고 서버 로그와는 시각으로 대조합니다)
- **분석·광고 beacon 차단**: 렌더마다 나가던 GA4 수집·광고 전환 요청을 차단해 통계 오염을 막습니다(48런/일 × 렌더 수십 회 규모). GitHub 러너는 IP가 유동적이라 GA4 내부 트래픽 필터(IP 기반)로는 거를 수 없어 발신 자체를 막습니다. 렌더에 관여하는 로더(gtag.js/gtm.js)와 SDK는 통과시키며, `page.route` 는 `page.request` 를 가로채지 않으므로 외부 링크 검증에는 영향이 없습니다
- **전체 재시도 없음**: 예전에는 CI에서 1회 재시도했는데, 오류 1건 때문에 9개 STEP이 통째로 다시 돌아 **서버가 불안정한 시점에 요청이 두 배**가 됐습니다(예산 가드도 시도별로 초기화). 오탐 방어는 아래 '실패 경로 재시도 정책'과 장애 지문으로 대체했습니다
- **실패 경로 재시도 정책(2026-08-01 개편)**: 전체 실행에 고정 지연을 추가하지 않고, **실패한 요청에만** 점진 백오프(2초 → 4초)를 붙입니다.
  - **4xx는 즉시 기존 판정으로 확정**합니다(재시도 없음). 예외는 '지연 404' 하나뿐입니다 — 오리진 간헐 장애의 실측 시그니처(no-store 경로 오리진 직격 → 10초대 지연 후 404)에 한해, **자사 호스트 + 멱등 GET + 응답 8초 이상**을 모두 만족할 때만 타임아웃 계열로 취급해 재시도합니다. 빠른 404·외부·비GET은 즉시 확정합니다.
  - **5xx·응답없음(0)·타임아웃은 재시도**합니다: 링크·네비게이션·API 재확인은 최대 3회(백오프 2s→4s), STEP1 본측정 샘플·크롤 네비·term 페이지·이미지(OG/DOM/STEP8)·설치 파일 Range 프로브는 2초 후 1회입니다.
  - **STEP1 워밍업 실패는 판정에서 제외**하고 본측정 3회 결과로만 판단합니다(워밍업은 연결 캐시가 목적). 본측정 중 **확정 실패(재시도 후에도 살아있지 않음)가 나오면 남은 샘플을 측정하지 않고 끊습니다** — 판정이 '하나라도 죽어 있으면 FAIL'이라 결과가 바뀌지 않는데, 전면 장애 시 STEP1 혼자 전체 예산을 소진하기 때문입니다(언어당 최악 146초 → 62초).
  - **인증서 점검은 순수 연결 타임아웃만 1회 재시도**합니다. 만료·호스트 불일치·검증 실패는 재시도로 달라지지 않는 확정 상태라 즉시 판정합니다.
  - **재시도 회복은 INFO**(스코어 미반영)로 남기고, 최종 실패는 기존 WARN/FAIL 그대로입니다.
  - **재시도 예산 게이트**: 재시도 시작 전에 **[경과 + 백오프 + 요청 timeout]이 안전 예산 `REPORT_SAFETY_MS`(510초) 안에 끝나는지** 확인하고, 부족하면 재시도를 생략한 채 최초 실패로 확정하며 기록에 `retrySkipped: 'budget'` 을 남깁니다. 기준을 600초가 아니라 510초로 두는 이유는, 재시도가 510초를 넘겨 이어지면 이후 검사가 예산 가드에 걸려 스킵되고 `coverageComplete: false` 가 되기 때문입니다. **510~600초 구간은 증거 생성·리포트 저장 여유로 보존합니다.**
    - **한계**: 이 게이트가 통제하는 것은 **재시도 경로뿐**입니다. 최초 요청·스크린샷·증거 생성 같은 다른 `await` 는 통제하지 못하며, 그중 하나가 멈추면 전체 타임아웃까지 끌려가 리포트·증거 저장이 실패할 수 있습니다. 즉 이 게이트는 **리포트 저장을 보장하지 않으며**, '재시도가 510초 이후까지 이어지지 않게 하는' 제한입니다. `REPORT_SAFETY_MS` 예산 가드도 마찬가지로 새 작업의 시작만 막을 뿐 진행 중인 `await` 를 중단하지 못합니다.
    - **DOM 이미지 locator 방어**: STEP5·STEP8의 `<img src>` 읽기는 호출당 2초로 제한합니다. 타임아웃이 나면 브라우저 채널이 멈춘 것으로 보고 같은 언어의 남은 DOM 이미지 순회를 중단해 `이미지 수 × timeout` 증폭을 막습니다. 이때 사이트 FAIL로 단정하지 않고 **WARN + `coverageComplete: false`** 로 미검증 수와 오류를 남긴 뒤, 다음 언어와 후속 STEP은 계속 실행합니다. 요소 detach 같은 비타임아웃 오류는 해당 요소만 건너뛰고 나머지를 계속 검사합니다.
- **장애 지문**: `report-status.json` 의 `failFingerprints` 에 `호스트+경로|오류계열` 형태 지문을 남깁니다(쿼리는 제외 — 같은 장애가 파라미터만 달라 갈라지지 않게).
  - 계산은 **`scripts/fail_streak.py` 한 곳**에 있고 **Slack 알림과 GitHub 이슈 생성 게이트가 이 스크립트를 공유**합니다. 둘 중 하나만 지문을 보면 이슈는 생성되는데 Slack은 조용한 식으로 어긋납니다.
  - 판정은 **누적 교집합**입니다. `{A,B} → {A} → {B}` 처럼 장애가 갈아타면 교집합이 비면서 연속이 끊깁니다. 매 런을 현재 지문과만 비교하면 서로 다른 장애가 3회 연속으로 잘못 계산됩니다.
  - **지문 이력이 없으면(지문 도입 전 이력·이력 유실·첫 배포) 지문 게이트를 걸지 않고 횟수 기준으로 폴백**합니다. 판정이 불가능한 상황에서 게이트를 걸면 실제 장애 알림이 통째로 죽습니다 — 과다 알림이 알림 누락보다 안전합니다.
  - 복구 알림도 같은 기준을 씁니다. 직전 런 시점의 판정을 재현하되 **직전 런의 지문은 이력에서 읽습니다** — 현재 런이 PASS면 `report-status.json` 의 지문이 비어 있어, 그걸로 재현하면 지문 판정을 포기하고 원시 횟수로 폴백해 A→B→PASS 에도 복구 알림이 나갑니다.
- **네트워크 실패 판정**: `requestfailed` 는 두 단계로 거릅니다.
  1. **우리가 차단한 요청은 `WeakSet<Request>` 기록으로 제외**합니다. 오류 문자열로는 구분할 수 없습니다 — `route.abort()` 기본값이 `failed` 이고 실측상 `ERR_FAILED` 와 `ERR_ABORTED` 가 섞여 나옵니다. URL Set이 아니라 Request 객체로 기록하는 이유는, 같은 URL이 나중에 진짜로 실패했을 때 그것까지 '우리가 막은 것'으로 오인하지 않기 위해서입니다.
  2. 남은 실패는 **실제 네트워크 오류 허용 목록**으로만 인정합니다(`ERR_FAILED`, `ERR_NAME_NOT_RESOLVED`, `ERR_CONNECTION_*`, `ERR_TIMED_OUT`, `ERR_ADDRESS_UNREACHABLE`, `ERR_INTERNET_DISCONNECTED`, `ERR_CERT_*`, `ERR_SSL_*`, `ERR_EMPTY_RESPONSE`, `ERR_CONTENT_LENGTH_MISMATCH`). 브라우저가 페이지 이동·레이아웃 변경으로 **스스로 취소한 `ERR_ABORTED` 는 장애가 아닙니다** — 이 단계가 없을 때 `_next/image` 프록시에서 실행 타이밍에 따라 나타났다 사라지는 오탐이 8건 발생했습니다. `ERR_FAILED` 는 `route.abort()` 기본값과 문자열이 같지만 우리가 막은 요청은 1단계에서 이미 걸러졌으므로, 여기까지 온 것은 실제 실패로 봅니다(미탐 방지). 차단 목록이 아니라 허용 목록인 이유는 모르는 오류를 장애로 올리지 않기 위해서입니다.
- **증거 수집**: 모든 FAIL·WARN에 시각 증거를 보장합니다. 예전에는 검사 항목마다 `captureShot()` 을 직접 불러서, 새 검사를 추가할 때 호출을 빠뜨리기 쉬웠고 실제로 API·설치 파일·SSL·OG 메타 이미지·예산 초과에는 증거가 없었습니다. 이미지 장애도 전역 플래그 때문에 첫 건만 찍혔습니다.
  - 기록은 **`recordIssue()` 단일 진입점**을 거칩니다. `failRecords.push()` 를 직접 부르는 곳은 이 함수 내부 한 곳뿐이라, 검사 항목이 추가돼도 지문 계산과 증거 확보가 자동으로 따라옵니다.
  - **화면으로 확인되는 장애**(UI·콘텐츠·로그인·다운로드 버튼·DOM 이미지·크롤·이지다운)는 **발견 즉시** 그 페이지를 촬영합니다. 요소 스크린샷이 가능하면 요소와 전체 페이지를 함께 남깁니다. 다른 곳으로 이동한 뒤 찍지 않습니다.
  - **화면에 나타나지 않는 장애**(API·설치 파일·SSL·OG/Twitter 메타 이미지·네트워크 실패·예산 초과·커버리지 0)는 **진단 카드**로 남깁니다. 운영 페이지를 이동시키지 않도록 **별도 페이지에서 `setContent()`** 로 렌더합니다(네트워크 요청 없음). 카드에는 STEP·유형·심각도·URL·HTTP 상태·증상·언어·감지 시각·응답 시간·`Content-Type`·`Content-Range`·네트워크 오류·실행 ID를 싣습니다.
    - 이미지 HTTP 실패는 이미 받은 응답에서 **참조 페이지·응답 크기·선별 헤더**(`server`, `via`, `x-cache`, `x-amz-cf-*` 등)와 **텍스트 오류 본문 발췌**를 함께 남깁니다. `Set-Cookie`·`Authorization` 같은 민감·불필요 헤더와 이미지 바이너리는 제외하며, 증거 보강을 위한 추가 네트워크 요청은 만들지 않습니다.
    - 서로 다른 간헐 오류가 종합 WARN으로 승격되면 카드의 **상세 내역**에 각 회복 STEP·언어·URL·최초 실패 원인을 모두 표시합니다. 집계 숫자만 보고 원인을 다시 로그에서 찾지 않아도 됩니다.
  - **지문당 파일 1장을 공유**합니다. 같은 장애가 4개 언어에서 반복돼도 이미지는 하나지만, **모든 기록에 `evidencePath` 가 채워집니다** — 증거 없는 장애 기록은 없습니다.
  - 리포트 저장 직전 **최종 보완**이 돌아 증거 없는 기록에 진단 카드를 만듭니다. 생성이 실패해도 런을 중단하지 않고 `evidenceError` 만 남깁니다. 결과는 `evidenceMissing` 필드로 확인합니다(0이어야 정상).
  - INFO 등급 외부 링크는 이지랩이 고칠 수 없는 제3자 자원이라 증거 필수 대상에서 제외합니다.
  - 각 기록에 `evidenceType`(`page`/`element`/`diagnostic`) · `evidencePath` · `evidenceError` 를 담고, Playwright HTML 리포트에도 첨부해 장애와 증거가 직접 연결됩니다.
- **점검 완주 여부**: 시간 예산으로 STEP을 건너뛰면 상태가 WARN이 되고, `coverageComplete: false` 와 `skippedSteps` 를 함께 내려 소비 측이 '전 항목 정상'과 '일부 미점검'을 구분할 수 있게 합니다
- **자동 리포팅**: 테스트 결과를 PASS/FAIL/WARN/SLOW/INFO 카운터로 집계하고 장애 리포트(개발팀 전달용) 자동 생성
- **실패 알림**: FAIL 감지 시 GitHub Issue 자동 생성(이미 열린 헬스체크 이슈가 있으면 중복 생성 대신 코멘트만 추가) + **Slack 알림**(신규 장애 / 장애 지속 중 매 점검 재알림 / 복구 전환)
- **네트워크 오류 대응**: Slack 발송은 일시적 오류에 대해 백오프 재시도(최대 4회)

## 4. 헬스체크 대시보드

GitHub Pages에서 누적 실행 이력을 다크모드 대시보드로 확인할 수 있습니다.

👉 **https://harry-qa.github.io/ezlab_healthcheck/**

- **지표 4종(2026-08-02 개편)**: 예전에는 `PASS / (PASS+WARN+FAIL)` 하나를 "Health Score"로 썼습니다. 산식에 WARN과 FAIL을 구분하는 항이 없어 **품질 경고가 장애와 똑같이 100% 감점**됐고, 그래서 **탐지 범위를 넓힐수록 가동률이 떨어지는 구조**였습니다. 실제로 OG 이미지 403 검사를 추가한 2026-07-31 직후부터 거의 모든 런이 WARN이 되어 8월 가동률이 0%로 표시됐습니다 — 사이트가 나빠진 게 아니라 검사가 늘어난 것입니다. 성격이 다른 질문 넷을 각각 답하도록 분리했습니다(산식은 `scripts/dashboard_metrics.py`, 규칙 테스트는 `scripts/test_dashboard_metrics.py`).
  - **서비스 가용률(내부 산식) / 최근 서비스 정상률(화면 표기)** = `가용 / (가용 + 장애)`. 런 분류는 **FAIL → 장애**, **PASS → 가용**, **WARN + 점검 완주 → 가용**(품질 경고는 있지만 사용자는 서비스를 쓸 수 있었음), **WARN + 미완주 · UNKNOWN → 확인 불가**입니다. 확인 불가는 분모에서 빼고 **건수를 카드에 함께 표시**합니다 — 판정하지 못한 런을 실패로 세면 헬스체크 자체의 문제가 사이트 점수로 둔갑합니다. `coverageComplete` 기록이 없는 과거 런의 WARN도 **임의로 가용 처리하지 않고 확인 불가**로 둡니다.
  - **점검 완주율(내부 산식) / 점검 완료율(화면 표기)** = `완주 실행 / 완주 여부를 아는 실행`. 예산 초과·크롤 중단으로 점검이 축소된 것은 사이트 문제가 아니라 헬스체크 자체의 건강 문제이므로 가용률에서 떼어냅니다. 표본이 10건 미만이면 비율 대신 `데이터 부족`으로 표시합니다.
  - **무경고 실행률(보조 지표)** = `PASS / (PASS+WARN+FAIL)`. 기존 Health Score와 같은 산식이지만 이름을 정확히 바꾸고 설명줄로 내렸습니다. **검사를 추가하면 낮아지는 것이 정상**인 지표입니다.
  - **열린 품질 경고(내부 명칭) / 확인이 필요한 항목(화면 표기)** = 장애 지문 단위로 중복 제거한 미해결 결함 수. 런 단위로 세면 결함 하나가 30분마다 새 경고로 잡힙니다(실측: "WARN 22건"이 실제로는 OG 403 하나가 22회 반복). **완주 실행에서 2회 연속 미검출이면 해결**로 전환하고, **미완주 실행은 해결 판정에서 제외**합니다 — 점검을 덜 한 런의 "안 보임"은 고쳐졌다는 근거가 아닙니다.
- **현재 서비스 표시**: `FAIL → 장애 감지` / `UNKNOWN·미완주 → 점검 결과 확인 필요` / `완주 WARN·PASS → 정상 운영 중`. 품질 경고 수는 현재 서비스 상태 문장에 중복 표기하지 않고 별도의 **확인이 필요한 항목**에서 보여줍니다.
- **집계 마이그레이션 (첫 운영 실행 전 1회 필수)**: 월별·일별 집계에 서비스 분류 벡터(`avail`/`outage`/`indet`)가 추가됐습니다. **일부 월에만 벡터가 있는 부분 마이그레이션 상태를 정상 데이터로 읽으면 안 됩니다** — 백필 전 월이 0%로 표시돼 "그 달에 서비스가 죽어 있었다"는 잘못된 결론이 나옵니다.
  ```bash
  git fetch origin gh-pages
  python3 scripts/backfill_stats.py /tmp        # 전 구간 재구성 + stats-meta.json 생성
  # 산출물을 gh-pages 루트에 반영: monthly-stats.json / daily-stats.json / coverage.json / stats-meta.json
  ```
  - 백필은 3단계로 검증하고, 어느 단계든 위반이면 **파일을 쓰지 않고 종료 코드 1로 중단**합니다(부분 마이그레이션 상태를 정상으로 표시하지 않기 위함).
    1. **재구성 결과(병합 전)** 에 불변식 `avail + outage + indet` = 이번에 읽은 실행 수
    2. **병합 결과**는 형태만 — 재구성이 본 구간의 벡터가 세 키를 모두 갖췄는지, 값에 음수가 없는지
    3. 재구성이 기존보다 크거나 같아 **벡터를 교체한 구간**만 병합 후에도 벡터합 = 실행 수
    합계 검증을 병합 결과 전체에 걸면 안 됩니다 — prune으로 폴더가 사라진 뒤 **기존 벡터 100건을 보존하고 남은 폴더 10건만 재구성한 정상 상황**에서도 `100 ≠ 10` 으로 실패합니다.
  - `stats-meta.json` 에 `schemaVersion: 2` 와 `backfillComplete: true` 가 **둘 다** 있을 때만 대시보드가 벡터를 신뢰합니다. 없거나 불완전하면 월별 지표는 **전 구간 보수적 환산**(WARN = 확인 불가)으로 통일되고, 월별 요약 헤더에 마이그레이션이 필요하다는 안내가 표시됩니다.
  - 재구성이 **더 적은 실행을 본 구간**(폴더가 prune된 과거)에서는 기존 벡터를 통째로 보존합니다. 벡터는 항목별 `max` 로 섞지 않습니다 — 섞으면 합이 실제 실행 수를 넘는 조합이 만들어집니다.
- **동일 실행 ID 재처리(upsert)**: `workflow_dispatch` 가 스케줄과 같은 분에 겹치거나 실패한 런을 재실행하면 같은 `YYYY-MM-DD_HH-MM` 키가 다시 들어옵니다. **이전 분류를 빼고 새 분류를 더하는 upsert** 로 처리해 원본 카운트와 서비스 벡터가 함께 이동합니다(같은 값이면 완전한 no-op). 단 `statuses.json` 은 최근 500건만 유지하므로 **그보다 오래된 런을 수동 재처리할 때는 백필로 재구성**해야 합니다.
- **최근 24시간 장애**: 최근 24시간 내 FAIL 건수(설명줄에 표시)
- **서버 첫 응답(TTFB) 추이**: 언어별(ko/en/jp/tw) 스파클라인, 최근 24회 · 위험 임계치 **500ms** (평균·최대·현재값 표기)
  - 응답 헤더(첫 바이트)까지만 측정해 본문 다운로드 시간을 제외(워밍업 1회 후 3회 중앙값). 서버 처리 체감에 가깝고, CI 러너↔서버 거리·본문 크기에 덜 흔들립니다.
- **SSL 인증서 만료**: `ezlab.im` / `ezdown.kr` 도메인별 만료까지 남은 일수(D-day)와 만료일을 미터로 표시(경고 D-14 / 장애 D-7 임계 시각화). 정상일 때도 항상 노출되어 만료 임박을 사전에 파악합니다.
- **일별 가동률(최근 90일)**: 날짜별 PASS/WARN/FAIL 히트맵
- **월별 요약**: 월별 **서비스 가용률** 도넛 차트(영구 보존). 세그먼트는 가용(초록)·장애(빨강)·확인 불가(회색)이고 가운데 숫자는 가용률이라, 확인 불가가 분모에서 빠지는 만큼 **세그먼트 비율과 가운데 숫자는 일부러 다릅니다**. 카드에는 WARN·FAIL·확인 불가 건수를 함께 적습니다. 새 집계 키(`avail`/`outage`/`indet`)가 없는 과거 월은 규칙대로 WARN을 전부 확인 불가로 환산합니다(없는 근거로 가용률을 올리지 않습니다).
- **실행 목록**: 월·일 아코디언 + PASS/WARN/FAIL 필터. 각 실행을 펼치면 서버 응답시간, cURL 재현 명령어, 장애 상세, 개별 Playwright 리포트 링크 확인

### 4-1. 판정 등급

점검 항목의 판정은 4단계이며, **이지랩이 고칠 수 있는 문제만 헬스 스코어에 반영**합니다.

| 등급 | 스코어 반영 | 런 상태 | 해당 사례 |
|---|:---:|---|---|
| **FAIL** | O | FAIL | 서버/API 응답 이상(404·5xx), 점검 페이지 노출, 로그인 페이지 진입 실패, 인증서 D-7 이하 |
| **WARN** | O | WARN | 이미지 로드 실패, 다운로드 버튼 미감지, 로그인 버튼 누락, 크롤 렌더 실패, 인증서 D-14 이하, 오리진 간헐 불안정(임계치 도달) |
| **SLOW** | X | 영향 없음 | 응답 3초 초과 — 느릴 뿐 정상 응답이므로 정보성 지표로만 집계 |
| **INFO** | X | 영향 없음 | 외부 링크(제3자 도메인) 응답 이상·접속 불가, **재시도 후 회복된 간헐 실패** — 기록은 남기되 스코어에서 제외 |

- **INFO를 스코어에서 빼는 이유**: 외부 링크는 이지랩이 소유·수정할 수 없는 제3자 서버입니다. 남의 서버 장애로 이지랩 가용성 점수가 깎이면 지표가 사이트 상태를 대변하지 못합니다. 깨진 링크 자체는 대시보드에 `참고 항목`으로 계속 노출되어 링크 교체·제거의 근거가 됩니다.
- **간헐 회복의 처리**: 재시도로 회복된 항목은 사용자에게 정상 페이지가 보인 경우이므로 개별 기록은 항상 **INFO**(스코어 미반영)로 남기고, 한 런에서 **서로 다른 정규화 지문이 2종 이상** 회복될 때만 `오리진 간헐 불안정` WARN 1건으로 승격합니다. 지문 기준인 이유: 같은 경로의 blip 하나가 4개 언어에서 반복 회복되면 건수로는 임계치를 넘기지만 실제로 흔들린 경로는 하나입니다 — 서로 다른 경로가 함께 흔들릴 때만 오리진 신호로 봅니다.

> **과거 기록 정정(2026-07-28)**: 응답속도 WARN → SLOW 분리(2026-07-13)와 간헐 회복 임계치 도입(2026-07-24) 이전에 기록된 판정이 gh-pages에 남아 스코어를 계속 깎고 있었습니다. `scripts/reclassify_warns.py`로 44건을 현행 기준에 맞게 정정했고, Health Score는 **92.6% → 98.6%** 로 회복했습니다. 정정 후 WARN으로 남은 4건은 모두 실제 이지랩 이슈입니다.

### 판정 규칙 테스트 (`tests/judgment.spec.ts`)

헬스체크 본체는 실제 사이트 상태에 따라 결과가 달라져서 판정 로직이 맞는지를 그것으로 확인할 수 없습니다. 특히 지금 운영에 떠 있는 결함이 고쳐지면 '그 결함을 잡는지'를 확인할 방법이 사라집니다 → **규칙은 운영 상태와 무관하게 여기서 고정**합니다.

검증 영역:

| 영역 | 확인 내용 |
|---|---|
| HTTP 상태 판정 | 2xx·3xx 정상 / 400·404·405·408·429·5xx·응답없음 실패 / 공개 경로 401·403 실패 / 로그인 페이지 200 기대 |
| 이미지 판정 | `Content-Type: image/*` 검사, 200인데 HTML·XML 본문, 본문 크기 0, 206의 `Content-Range` 유효성 |
| 설치 파일 Range 프로브 | 206 + `bytes 0-0/N` + **수신 바이트가 정확히 1** 일 때만 통과(0바이트·2바이트 이상은 실패), Range 무시(200) 처리 |
| 네트워크 실패 | 실제 오류(`ERR_FAILED`·DNS·연결·타임아웃·인증서 등)는 장애, 브라우저 자체 취소(`ERR_ABORTED`)·차단(`ERR_BLOCKED_BY_CLIENT`)·사유 없음은 무시 |
| 장애 지문 | 쿼리 무시, 오류 계열 구분, 콘텐츠 누락 분류 |
| 증거 수집 | FAIL·WARN은 증거 필수·INFO는 제외, 지문당 파일 1장 공유, 기존 증거 보존, 생성 실패 시 `evidenceError`, 보완 후 누락 0건 |

장애 지문의 **연속 판정**은 `scripts/test_fail_streak.py` 가 검증합니다 — 누적 교집합(`{A,B}→{A}→{B}`), A→B 억제, 지문 이력 부재 시 폴백, 그리고 복구 알림 시퀀스(A→B→PASS 억제 / A→A→PASS 발송)입니다.

**두 테스트 모두 CI에서 헬스체크보다 먼저 실행되며, 실패하면 런이 중단됩니다.** 판정 규칙이 깨진 채로 나온 헬스체크 결과는 신뢰할 수 없기 때문입니다.

Slack 알림은 `DRY_RUN=1` 로 발송 없이 미리보기할 수 있습니다.

```bash
DRY_RUN=1 SLACK_WEBHOOK_URL=x HEALTH_STATUS=FAIL RECENT_STATUSES=FAIL,PASS \
  RUN_DATETIME=2026-07-31_00-47 python3 scripts/notify_slack.py
```

### 아직 검증되지 않은 것

로컬 실행과 규칙 테스트로 확인한 범위 밖은 다음과 같습니다. 배포 전에 감안해야 합니다.

- **CI 환경 미실행** — 러너 지역·네트워크가 로컬과 달라 실행 시간, 간헐 실패 빈도, `ERR_ABORTED` 발생 패턴이 다를 수 있습니다. **운영 반영 전에 브랜치에서 `workflow_dispatch` 로 수동 실행해 확인하는 것을 권장합니다.**
- **변경 전후 요청량·실행시간 A/B 미측정** — 비교는 CI 런끼리, **같은 job 안에서 전후를 연속 실행**해야 의미가 있습니다. 로컬은 서버까지 거리가 다르고 프로세스가 throttling되면 값이 통째로 흔들려 기준선으로 쓸 수 없습니다(실제로 로컬 시도에서 한쪽 조건이 예산 가드에 걸려 `coverageComplete: false` 로 끝나 비교가 무효였습니다).

  A/B는 `.github/workflows/ab-network-policy.yml` 이 수행합니다. **참고용 리포트가 아니라 게이트**로, 아래 중 하나라도 어긋나면 실패로 끝납니다.

  | 검사 | 실패 조건 |
  |---|---|
  | 리포트 생성 | 각 조건 실행 후 `report-status.json` 이 없음(미완주) |
  | 표본 수 | `off`/`on` 결과 개수가 `repeats` 와 불일치 |
  | 점검 완주 | 어느 런이든 `coverageComplete !== true` |
  | 증거 누락 | 어느 런이든 `evidenceMissing !== 0` (또는 필드 없음) |
  | 실행 시간 | 어느 런이든 8.5분(510초) 예산 초과 |
  | 요청 증가 | 브라우저 자사 요청 중앙값 증가가 임계(기본 +10%) 초과 |

  실행 전 매번 `report-status.json` 을 지웁니다 — 안 지우면 이번 실행이 리포트를 못 만들었을 때 직전 조건의 결과를 복사해 A/B가 조용히 오염됩니다. 조건 순서도 **회차마다 뒤집습니다**(1회차 off→on, 2회차 on→off). 순서를 고정하면 먼저 도는 조건이 CDN·오리진을 데워 '조건'과 '실행 순서'가 결합됩니다.

  **실행 순서 (중요)** — `workflow_dispatch` 는 워크플로 파일이 **default branch(main)에 있어야** 트리거됩니다. 따라서 다음 순서로 진행합니다.

  1. 작업 브랜치 푸시 (코드 변경 전부)
  2. **A/B 워크플로 파일만 main 에 먼저 반영** — 스케줄 트리거가 없어 운영 동작은 바뀌지 않습니다
  3. `gh workflow run ab-network-policy.yml --ref <브랜치> -f repeats=3` 으로 브랜치 코드 기준 A/B 실행
  4. 게이트 통과 확인 후 나머지 변경을 main 에 병합

  브랜치 CI가 한 번 성공한 것은 A/B 통과가 아닙니다.
- **요청 계측 범위** — 리포트의 `requestCounts.own`/`third` 는 **브라우저가 낸 요청만** 셉니다(`scope: 'browser-only'`). `page.request` 로 보내는 링크·이미지·API·파일 Range 검증, `measureTTFB` 의 raw HTTPS, 인증서 TLS 핸드셰이크는 포함되지 않습니다. `HC_NET_POLICY=off` 도 '식별 헤더 전체 해제'가 아니라 **브라우저 라우팅 헤더와 beacon 차단만 해제**입니다 — `page.request` 계열은 라우팅을 타지 않아 off 에서도 식별 헤더를 그대로 보냅니다.
- **CloudFront 캐시 정책 미확인** — `ezlab.im` 정적 자산이 GET·HEAD 모두 반복 MISS로 관측됐으나 원인이 확정되지 않았습니다. 이 때문에 헬스체크 식별 헤더는 **상수 하나(`X-Ezlab-Healthcheck: 1`)만** 보냅니다. 런마다 바뀌는 값을 헤더로 실으면 캐시 키가 분산될 수 있어, 정책이 확인되기 전까지는 실행 ID를 요청에 싣지 않습니다(리포트의 `runId` 로만 남깁니다).

### 유지보수 스크립트

집계 파일이 손상됐거나 판정 기준이 바뀌었을 때 쓰는 스크립트입니다. 둘 다 gh-pages 체크아웃을 대상으로 동작하므로, 작업 전용 워크트리를 떠서 실행한 뒤 결과를 확인하고 커밋하세요.

```bash
# gh-pages 작업본 준비
git fetch origin gh-pages
git worktree add /tmp/ghp origin/gh-pages --detach

# 집계 파일 재구성 (statuses / perf / daily / monthly) — 손상·유실 복구용
python3 scripts/backfill_stats.py /tmp/ghp

# 판정 기준 변경에 맞춰 과거 WARN 정정 — 반드시 dry-run으로 먼저 확인
python3 scripts/reclassify_warns.py /tmp/ghp            # 검토만 (파일 변경 없음)
python3 scripts/reclassify_warns.py /tmp/ghp --apply    # 실제 반영

# 확인 후 커밋·푸시
cd /tmp/ghp && git add -A && git commit -m "..." && git push origin HEAD:gh-pages
git worktree remove /tmp/ghp
```

> `reclassify_warns.py`는 루트 집계뿐 아니라 **개별 실행 폴더의 `status.json`도 함께 정정**합니다. `backfill_stats.py`가 실행 폴더를 원본으로 집계를 재구성하기 때문에, 루트만 고치면 다음 백필 때 낡은 판정이 되살아납니다. 두 번 실행해도 결과가 같습니다(멱등).
